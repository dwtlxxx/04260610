# 开发流程与约定（AI / Coding Agent 协作规范）

> 本文件是「我（AI Agent）」与「你（开发者）」之间的协作契约。每次开工前以此为准。

---

## 一、总原则

1. **先拆解、后动手**：拿到需求先输出「需求拆解」，你确认后再写代码。
2. **有疑惑必须问**：不猜测你的意图；关键分叉点一律先问，问清楚再动手。
3. **可运行优先**：宁要 3 个能跑的功能，不要 10 个半成品。每个里程碑结束时项目必须能打开、能用。
4. **可回退**：每个里程碑一次独立 Commit；出问题能一键回到上一个可用状态。
5. **面向你的说明一律中文**：README、注释、交付说明、报错解释全部中文。

---

## 二、标准工作流（每个功能都走一遍）

```
① 需求拆解  → ② 你确认 → ③ 实现最小可用版本 → ④ 本地自测（含异常场景）
   → ⑤ 提交 Commit → ⑥ 你验收 → ⑦ 下一项
```

### ① 需求拆解要输出什么

- 目标用户是谁、在什么场景下用
- 真实痛点是什么（而不是「看起来有用」）
- 核心功能（必须做）/ 次要功能（有空再做）/ **明确不做**（这是取舍，评分看重）
- 技术方案与风险点（哪里可能翻车、备选方案是什么）
- 拆成几个可独立提交的任务，顺序是什么

### ③ 实现约束

- **默认技术栈**：`HTML + CSS + 原生 JavaScript`
  - 理由：GitHub Pages 可直接发布，零构建、零依赖、零部署风险
  - 仅在功能确实需要时才升级到 Vite + React/Vue，且必须提前说明部署方式的变更
- **不引入后端**：考核明确要求核心体验不依赖服务器；数据用 `localStorage` 持久化
- **不写死敏感信息**：不出现账号、Token、API Key(值)
- **健壮性**：边界输入（空值、超长文本、重复数据）必须处理；`localStorage` 读写包一层 `try/catch`

### ④ 自测清单

- [ ] 正常流程走通
- [ ] 空输入 / 极端输入不崩
- [ ] 刷新页面后数据仍在（如涉及持久化）
- [ ] 浏览器 Console 无红色报错
- [ ] 窗口缩放到手机尺寸布局不乱

## 三、项目目录规范

**每个项目一个独立子文件夹**，与文档、配置分离：

```
04260610/                     # 仓库根
├── README.md                 # 仓库总说明（评委第一眼看的）
├── .gitignore
├── .nojekyll                 # GitHub Pages 必需
├── docs/                     # 过程文档
├── _keys/                    # SSH 密钥（已被 .gitignore 忽略，绝不提交）
└── <项目名>/                  # 例如 todo-app/
    ├── index.html            # 入口页面（Pages 需要它）
    ├── css/style.css
    ├── js/app.js
    ├── assets/
    └── README.md             # 该项目自己的说明（可选）
```

> ⚠️ **Pages 入口陷阱**：`https://dwtlxxx.github.io/04260610/` 只会在**仓库根目录**找 `index.html`。
> 若源码放在子文件夹 `todo-app/`，则访问地址是 `.../04260610/todo-app/`。
> 若要根路径直接可用，需在根目录放一个 `index.html` 作为入口（跳转页或就是作品本身）。
> **建议**：正式作品直接把 `index.html` 放在仓库根目录，结构最简单、最不容易出错。

## 四、Commit 规范

格式：`类型: 做了什么`

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复问题 |
| `docs` | 文档变更 |
| `style` | 样式调整（不影响逻辑） |
| `refactor` | 重构 |
| `chore` | 杂项（初始化、配置） |

要求：
- 一次提交只做一件事，粒度可运行
- **禁止** `update`、`修改`、`1` 这类无意义信息
- **禁止** 在提交信息或代码中出现密钥、Token

---

## 五、报错处理流程（体现「问题解决与学习迁移」）

```
① 完整读一遍报错（含文件、行号）
② 定位是「语法 / 路径 / 逻辑 / 环境」哪一类
③ 说出最可能的原因假设
④ 用最小改动验证假设
⑤ 修好后说明为什么这样修，以及如何避免同类问题
```

## 六、时间管理（120 分钟参考分配）

| 阶段 | 时长 | 产出 |
| --- | --- | --- |
| 读题 + 需求拆解 | 15 min | 拆解文档，明确「做什么 / 不做什么」 |
| 骨架 + 首次 Commit | 15 min | 能打开的空壳页面，已 push |
| 核心功能 | 45 min | 主功能可用，第 2 次 Commit |
| 交互与细节打磨 | 25 min | 状态提示、边界处理，第 3 次 Commit |
| 部署 + 自检 | 15 min | Pages 链接可访问，5 项自检全过 |
| 缓冲 | 5 min | 应对意外 |
